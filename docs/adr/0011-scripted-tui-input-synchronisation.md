# Scripted TUI tests synchronise on the child's terminal-control bytes, never on elapsed time

[ADR-0009](0009-acceptance-test-harness.md) §6 fixed that acceptance tests drive the *built binary*. Driving a terminal UI that way needs a rendezvous the process boundary does not give for free: the test must know the child has taken the terminal before it writes a key press. The original driver guessed, sleeping a fixed 500 ms. This ADR fixes how that rendezvous is actually established.

1. **The gate is the child's own output, in two stages.** The driver reads the child's pseudo-terminal until it sees the alternate-screen switch (`\x1b[?1049h`), then until the tail of a ratatui frame flush (`\x1b[0m`) appears *after* that switch. The first proves the PTY is raw, because crossterm enables raw mode before it emits the switch (`src/tui.rs:138`); the second proves a frame was painted and the TUI is parked on its event read. Only then is input written. Wall-clock sleeps are rejected as a readiness signal anywhere in this driver: a key press written while the line discipline is still canonical is echoed and reshaped rather than delivered, and the TUI then blocks on an event read that never arrives.
2. **No rendered glyph can serve as the sentinel.** `script(1)` sizes its pseudo-terminal from a `TIOCGWINSZ` on its own stdin; the driver pipes stdin, so the ioctl fails and the child gets a 0x0 window. Ratatui paints an empty frame — the entire first draw is `\x1b[39m\x1b[49m\x1b[59m\x1b[0m\x1b[?25l`. Matching the banner wordmark or a mark glyph is therefore not an option, and the escape sequences are the only signals available. This is recorded because the glyph approach is the obvious one and it silently cannot work.
3. **Both child pipes are drained concurrently, on background threads.** Observing output while the child still runs rules out `wait_with_output`, and leaving either pipe unread risks a full pipe stalling the TUI. The returned `Output` is assembled from the drained buffers, so callers see exactly what they saw before.
4. **The bound is a generous timeout plus early exit on pipe close.** A slow host must never fail — the ceiling is 30 s against a startup that normally takes single-digit milliseconds. A child that exits without taking the terminal closes the pipe, which ends the wait immediately and fails with the captured transcript instead of burning the ceiling. The distinction is deliberate: slow is not the same as wedged.
5. **Every path that gives up on the child tears down its process group first.** The readiness gate introduces failure paths that abandon the child *before* any key press is written, and those are bound exactly like a bad key sequence: SIGTERM, then SIGKILL if it has not exited within five seconds. A test that fails must not leave a live PTY for the next one to inherit, whatever the reason it failed.
6. **The `before_input` hook is unchanged.** It still fires immediately before the write, now against a TUI provably past its plan snapshot.
7. **Staging between two key scripts is a rendezvous too, on stage boundaries.** `vibesync_in_tty_with_staged_input` writes a first key script and must then let a filesystem change land in a *named stage*, not merely some time later. It waits for the two screen clears `run_pair_flow` emits — the pane gate proceeding into Compare (`src/tui.rs:1057`), then the finished scan handing its plan to Review (`src/tui.rs:1081`) — and finally for the frame Review paints. A flat sleep here was worse than a flaky one: a Compare slower than the delay moves the change *inside* the scan, so the test silently exercises a different scenario than its name claims while still passing. The next frame flush cannot substitute for the clears — Compare draws on entering the stage, before it has read the key that starts the scan, and again every 50 ms for as long as the scan runs (`src/tui.rs:441`), so a flush proves nothing about the scan's progress.

## Consequences

- The harness is now coupled to three third-party behaviours: crossterm enabling raw mode before switching screens, ratatui ending every flush with an attribute reset, and ratatui clearing with `\x1b[2J`. A `crossterm` or `ratatui` upgrade that changes any of them breaks the tests loudly at the gate, with the transcript in the panic message — a visible failure at a named point, not a silent return to guessing.
- §7 additionally couples the staged driver to `run_pair_flow` clearing exactly once per stage entry. That is first-party code, and the same loud failure applies: adding or removing a clear on the path into Review fails the staged tests at their gate rather than quietly shifting what they test.
- Any future test that intentionally drives a `vibesync` invocation which exits *before* taking the terminal needs a different helper; this one asserts that the TUI starts.
- Suite wall time is unchanged in practice (~1.8 s for `--test cli` before and after on a 16-core host, where the sleeps overlapped across parallel tests). The gain is determinism, not speed; on a host with few enough cores to serialise these tests, removing six 500 ms sleeps also helps.
- ADR-0009's fault-injection harness is untouched — different file, different purpose. This ADR governs `tests/cli.rs`'s TUI driver only.
